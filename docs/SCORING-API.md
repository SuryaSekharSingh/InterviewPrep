# AI scoring API

The Python backend uses local Ollama to evaluate technical/HR interview answers, written English introductions and subject-test short answers. Objective MCQ and code-output answers are checked against the published answer key. The backend calculates totals from validated rubric dimensions; the model cannot supply a final total or change the weights.

## Request scoring

`POST /api/v1/activities/{activityId}/scoring`

Send `Authorization: Bearer <session token>`, `Content-Type: application/json`, and an empty JSON object:

```json
{}
```

Only the owner can request or retrieve an activity's score. Answers, question references, review criteria and weights come from stored server records. Additional body fields such as `score`, `answer`, `reference` or `weights` are rejected.

- **Test:** save responses with the existing response endpoint, then request scoring to close and grade the test.
- **Interview:** submit at least one answer with the existing interview answer endpoint. Requesting activity scoring finishes the interview and evaluates accepted answers. Do not call this endpoint after every turn; ordinary answer submission already queues each turn's evaluation.
- **English:** submit a written self-introduction through the English submission endpoint. Scoring runs automatically; this endpoint can retrieve/retry the same accepted work. An empty activity cannot be scored.

The request returns HTTP 202 when queued and HTTP 200 when a final result can be reused. Requests for the same activity reuse the saved job or report. Poll the matching GET endpoint while processing:

`GET /api/v1/activities/{activityId}/scoring`

Example response shape (illustrative):

```json
{
  "activityId": "activity-uuid",
  "module": "TEST",
  "state": "RUNNING",
  "jobId": "job-uuid",
  "score": null,
  "eligible": false,
  "provisional": false,
  "retryable": false,
  "errorCode": null,
  "report": null
}
```

## States and failures

| State | Meaning |
|---|---|
| `NOT_REQUESTED` | The activity has no requested final score yet. |
| `QUEUED` / `RUNNING` | Accepted work is waiting/processing. A missing score is not zero. |
| `COMPLETED` | A report exists; `score` can still be null if no answer was scorable. |
| `NEEDS_REVIEW` | A short answer could not be scored reliably; manual review is needed. |
| `FAILED` | Processing failed. Saved answers and available objective results remain accessible. |

If `retryable` is true, repeat the POST or use `POST /api/v1/jobs/{jobId}/retry`. At most five processing attempts are allowed. Completed scores are not regenerated by repeating the request. Validation failures return 422, missing authentication 401, unknown/unowned activities 404, and incompatible states or exhausted retries 409.

Short-answer AI marks are explicitly provisional and do not contribute to progress until an administrator reviews them. An unscorable short answer has null points and prevents a misleading complete test total. Objective subtotals remain available if AI is unavailable. Admin review is blocked while grading is running to prevent conflicting updates.

## Rubrics and feedback

Dimensions use anchored ratings from 0 to 4: absent/incorrect, major gaps, partial, mostly correct, complete. The backend computes `sum(rating × weight) × 25` and rounds to two decimal places.

| Kind | Weights |
|---|---|
| Technical interview | Correctness 40%, reasoning 30%, clarity 20%, relevance 10% |
| HR interview | Relevance 30%, structure 25%, clarity 30%, reflection 15% |
| English | Grammar 30%, clarity 35%, relevance 35% |
| Short answer | Correctness 75%, clarity 25% |

Saved feedback includes dimensions, exact evidence excerpts, strengths, improvements, suggested wording, model identifier, evaluation timestamp, `rubricVersion` and `scoringVersion`. Invalid types, missing/extra fields, non-finite values, out-of-range ratings and evidence absent from the answer are rejected before a score is saved. New evaluations use `rubric-v3` and `weighted-v2`; existing historical feedback remains stored as originally produced.

For technical and HR interviews, any understandable, on-topic answer marked scorable receives at least 10/100. The backend applies this minimum through the relevance dimension, so the saved dimensions still add up to the displayed score. Correctness and reasoning remain independently rated; a relevant but incorrect answer can therefore receive the minimum without being treated as correct. Unrelated or unintelligible answers stay unscored. This policy is recorded as `rubric-v3` and `weighted-v2`; it does not change English or subject-test scoring. Existing completed reports keep their original scores.

English feedback assesses written grammar, clarity and relevance. A failed interview follow-up falls back to published seed content while keeping the saved evaluation.

## Tests

Run the standard suite using the test-database environment described in the README:

```powershell
.\.tools\python-backend\Scripts\python.exe -m pytest backend-python/tests -q -p no:cacheprovider
```

Live model checks are opt-in. They use synthetic answers and require local Ollama with `qwen3:4b` plus the dedicated `interviewedge_test` database:

```powershell
$env:EDGE_LIVE_AI = 'true'
.\.tools\python-backend\Scripts\python.exe -m pytest backend-python/tests/test_live_scoring.py -q -s -p no:cacheprovider
Remove-Item Env:EDGE_LIVE_AI
```

These tests verify software behavior and a small sample of real-model outputs. The wider faculty/reviewer calibration set remains a release requirement.
